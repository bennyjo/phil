## 2. Data-integrity correction: Aug 2026 core CPI MoM was 0.3%, not 0.2%

This is the substantive finding of the cycle. The TRIGGERED candidate
(pricemove:2252245, Fed 25bp-hike market) had moved 0.605→0.755 (live book
now bid 0.78/ask 0.79, oneMonthPriceChange +0.46) — a huge, unexplained-by-
the-stored-note move, since the note on file describes the OPPOSITE
scenario ("a move toward 0.40 re-opens the cross-market gap"). Researching
why surfaced the cause and, in the process, a factual error in this
session's own prior output.

The immediately preceding FULL cycle (commit 2808bee, 12:32:46Z) logged:
"TradingEconomics calendar... shows August 2026 core CPI MoM printed
0.2%... treat as provisional until a primary BLS confirmation lands" and
cited market corroboration: "the core-MoM-0.2 CLOB book... moved from ~0.5
pre-release to bid 0.72/ask 0.92."

Both were wrong, and the cycle's own "provisional" hedge is exactly why
this didn't propagate further:

- **Primary BLS source** (bls.gov/news.release/cpi.nr0.htm, fetched this
  cycle): "Core CPI... rose 0.3 percent after increasing 0.2 percent in
  July" — headline MoM 0.4%, headline YoY 3.4%, core YoY 2.4%.
- **TradingEconomics primary page** (not the calendar list used before):
  confirms 0.3%, "above market forecasts of a 0.2% rise."
- **The market's own sibling bracket set**, checked directly by market ID
  today (all `umaResolutionStatuses: ["proposed","proposed"]`, i.e.
  post-release and settling):
  - 3539687 "Core CPI MoM be 0.2%?" → ask 0.006 (effectively NO)
  - 3539688 "Core CPI MoM be 0.3%?" → bid/ask 0.999/1.0 (effectively YES)
  - 3539696 "Core CPI YoY be 2.4%?" → 0.991/1.0 (YES, matches BLS)
  - 3539666 "headline MoM 0.3%?" → ask 0.009 (NO; BLS actual is 0.4%)
  - 3539673 "annual inflation 3.3%?" → ask 0.001 (NO; BLS actual is 3.4%)

So the "core-MoM-0.2 book at bid 0.72/ask 0.92" read at 12:2xZ was a
**transient immediate-post-release mispricing** (traders reacting before
the exact BLS decimal was digested, or a stale/thin quote caught mid-move)
that had fully reversed by ~12:4xZ once the print settled into general
awareness — the two brackets (0.2% and 0.3%) were briefly both elevated,
which is itself internally inconsistent for a bracket set and should have
been the tell.

**Why this matters beyond one log line:** this cluster gates 11 open
forecasts (`journal/screener` Sep7 CPI batch: headline/core MoM and YoY
buckets, `5a6d5321c25a`/`79e72c3002c3` veto rows included) that
`schedule.json`'s watch item says to "GRADE AT SETTLEMENT... once
resolve.py/UMA catches the close." If that grading had used the wrong
0.2% figure as ground truth, several of those forecast rows would have
been graded backwards (e.g. a forecast centered on 0.2% would have looked
right instead of wrong, and vice versa for 0.3%). resolve.py itself is
unaffected — it settles off the actual on-chain/UMA resolution, not off
this log's belief — so no ledger or forecast was mis-settled. The risk was
entirely in this agent's own qualitative grading text, caught before any
of those 11 rows have actually settled (all still "proposed", not final).

### Playbook lesson (encoded)

Added to the fact-finality section: once a bracket-set market's
`umaResolutionStatus` moves to "proposed", checking the bracket siblings
directly by market ID is a cheap, sharp, near-zero-ambiguity way to pin an
exact print value — sharper than a calendar aggregator and available
before a primary-source page catches up. And: an immediate post-release
CLOB read is not yet settlement corroboration — a bracket set where two
adjacent buckets are both elevated at once is internally inconsistent and
should be flagged as "still moving," not read as confirming either one.
Wait for `proposed` (or check the sibling set for a clean single-winner
pattern) before citing "the market confirms X" for an exact numeric print.
